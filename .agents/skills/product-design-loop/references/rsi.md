# Execution learning and recursive self-improvement

Use this only when a product-design-loop run exposes a reusable process limitation,
an exploratory run is meant to inform a project/architecture decision, or the user
asks to evaluate the method. It is proposal guidance, not an autonomous
self-modification loop.

## Start from observed evidence

Use the actual goal or hypothesis, candidate/skill revision, relevant checks or UI
observations, review findings and missing evidence. Prefer links to permitted
evidence over copied transcripts. Never publish secrets, private snapshots, raw
agent conversations, hidden reasoning or unrestricted runtime/browser artifacts.
Distinguish facts, reproducible mechanisms and hypotheses. Do not invent a failed
round, recurrence or stronger claim than the run supports.

Locate the owner before proposing a change:

- a product defect belongs in product code;
- a missing or ambiguous project authority belongs with that project;
- a procedural ambiguity may justify a skill change;
- an unavailable or unenforceable capability is a tooling/runtime limitation.

Do not add several layers for one observation.

For a probe/prototype, preserve the decision target. State which observation
actually distinguished alternatives and which conditions remain untested. A
successful pilot proves the exercised scenario, not the architecture in general.
A failed pilot may identify a local defect or environment limit rather than falsify
the whole direction. Prefer prototypes whose result can change a decision.

## Reduce context rather than create another authority

Generalize only a rule that would improve another relevant task. A local command,
selector, framework convention, fixed delay or screenshot is not a universal rule.

If agents repeatedly need unrelated material to recover stable design intent, an
accepted structured design contract such as `DESIGN.md` may reduce context. Propose
it only when the demonstrated burden justifies another maintained artifact. Keep
one canonical owner for each fact; use generated projections, links or guidance
instead of copying product, runtime, verification, security or token facts into a
second hand-maintained source.

Likewise, do not create a new configuration file, issue taxonomy, evidence store,
runtime or checker merely because the generic skill needs somewhere to put an
answer. Prefer an existing authority and native capability.

Architecture observations from exploratory runs are roadmap input, not roadmap
authority. Identify the smallest capability gap actually demonstrated before
proposing a framework or host-level mechanism.

## Make a decision-ready proposal

Report only material proposals, using:

- **Observation:** run intent, candidate/skill identity, inspectable evidence and
  missing observations; for a probe, include the decision target.
- **Mechanism:** why the current process added risk or unnecessary context, with
  applicability and limits.
- **Smallest change and owner:** the minimal skill, project-authority or tooling
  change that addresses the observed mechanism.
- **Validation:** what later observation should improve and what counter-case must
  remain valid; state what would disprove the proposal.

No suggestion quota, quality score or mandatory multi-agent evaluation. If no
reusable lesson is supported, say so briefly.

## Apply accepted changes at the owner

Only after separate authorization, re-read the current owner and make the smallest
complete change there. Skill procedure belongs in the existing `SKILL.md` or this
reference; project facts belong in project authority; tooling gaps belong in their
implementation.

Do not create a `v2` skill, permanent lessons journal or parallel authority. Do
not change acceptance rules mid-task to convert failed evidence into success.
Validate the changed boundary with representative behavior; wording checks alone do
not prove better agent decisions. Keep ordinary execution history in existing
project reports rather than a new telemetry or evidence database.
